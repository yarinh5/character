# WP11 admin user directory (2026-11-26)

- Cause: `/admin/users` read profiles and role rows without pagination, so API row limits could hide older users and local filters could report false absence. A missing role was silently labeled `client`.
- Change: a forward-only, admin-gated RPC applies search, role and status filters before a stable `(created_at, user_id)` page. The server calls it with the authenticated admin JWT, and the UI loads 100 rows at a time with one lookahead row. A missing role is shown as unassigned; it is not implicitly written as `client`. Later-page errors preserve loaded rows and allow retry.
- Checks: focused server and UI tests cover the authenticated boundary, invalid inputs, missing role, continuation, server search and later-page failure. Typecheck and changed-file lint passed. A pgTAP case was added for authorization, role precedence, filters and cursor ties.
- Remaining acceptance: the migration and pgTAP have **not** run against PostgreSQL; live admin route and Product integration are unverified. This is an Offline implementation, not WP11 or Product PASS.
- Write-path correction: a self role-change request now fails before email or profile mutations. RED reproduced the previous partial-write path; GREEN passes the server-boundary regression. A further forward-only RPC now replaces the role, maintains the operator/client auxiliary row and writes the role-change audit in one DB transaction. Server-boundary tests confirm creation and update use that authenticated RPC rather than independent service-role writes. The pgTAP transaction/rollback tests are written but **NOT RUN live**.
- Auth user creation and email changes remain external to the DB transaction. A failure between Auth and DB can leave a partial update; the UI must not claim those cross-service operations are atomic. Live integration must verify the new RPC before WP11 acceptance.
- Reset-link feedback: a clipboard rejection no longer produces a false "copied" success. A focused UI regression reproduced the old behavior and passes after the scoped change; reset-link generation and delivery contracts were not changed.
- User soft-delete feedback: profile lookup, missing target, profile update and operator deactivation now fail before success/audit; RED reproduced false success for the DB error paths and focused server regressions pass. The two DB writes are still separate, so an operator-write failure can leave the profile blocked; live integration and a transactional lifecycle contract remain open before WP11 acceptance.
- User status safety: the quick status action and edit form now apply the same Auth ban as client status management; blocking bans before profile mutation, and reactivation unbans only after the profile write. Self-status changes and reactivation of archived/PII-archived profiles are rejected. Soft-delete bans Auth before its DB writes. These cross-service operations are not atomic; client archival/PII deletion remains a distinct workflow and was not redefined here.
- Admin link safety: impersonation and password-reset link generation now require an active, non-archived target and surface profile lookup errors. RED reproduced link creation for blocked/archived users and a masked DB error; focused GREEN passes. Live Supabase Auth behavior is still unverified.
- Independent lifecycle review: generic soft-delete could target another admin while leaving `user_roles.admin` intact. It now rejects that target before Auth/profile changes; RED/GREEN server regression passes. Remaining distinct gaps: generic delete does not set a durable archive marker, generic activation does not check confirmed WP10 deletion requests, and role transition may set an archived operator active. These require focused follow-up; none is proven live.
